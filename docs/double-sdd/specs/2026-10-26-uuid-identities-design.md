# Global UUID identities for trusted collaboration

## Authorization and intent
The user explicitly accepts UUID plus nickname identities, project-independent creation/selection, cross-project reuse and identity-file transfer between computers. Passwords, signatures, impersonation prevention and servers are unnecessary for trusted internal teams. The user asks to start and complete work autonomously, retaining prior authorization not to pause for spec approval. Earlier instruction explicitly says deployed-data compatibility/migration is not needed. Do not modify user NAS projects, source recordings or old releases during development.

## Decision and current evidence
Current accounts generate a different author UUID per project and require Argon2 credentials; the automatic local identity also depends on DPAPI. Private workspaces already key by canonical project root, project ID and author UUID. Preserve this separation and the existing per-author writer lock, publication/revision checks and lifecycle barriers.

Alternatives considered: optional password-free records alongside account records; a new profile store layered over legacy login; a clean UUID author model with an explicit collaboration format boundary. The clean model is selected: the first two retain unwanted account semantics and two identity systems. A bounded roundtable (YAGNI Minimalist and Operations Owner) agreed on this choice and highlighted format-2 conditionals, stable author-session authority and transactional selection. Their suggestion to omit renaming is not adopted because the preceding accepted design explicitly allows changing nicknames without changing UUIDs.

## User experience
- Application-level identity state is available before any project opens. On the first successful load create one UUID-v4 identity with a recognizable default nickname such as `本机身份 · <8-character UUID prefix>`; persist it before using it. Remember the selected identity across restarts. No registration, password, login/logout or guest-to-account conversion UI.
- The compact collaboration menu shows the current nickname and provides `创建身份…`, `切换身份…`, `修改昵称…`, `导入身份…`, `导出当前身份…`. A single compact identity dialog may contain these operations; the menu must be usable on the empty workspace. Project sync/author actions remain disabled until their project requirements are met. Do not add a permanent explanatory banner or consume another toolbar row.
- Creation asks for a nickname and offers `创建并使用`. Persistence of a created profile precedes selection; if selection is refused, the new profile remains available and the previous active identity remains selected, with a visible error. Import adds a profile without switching; the result can offer `使用此身份` explicitly. Selection is one explicit action.
- Identity list distinguishes duplicate nicknames by a short UUID; full UUID is available to inspect/copy. Nicknames need not be unique. Selecting the already-active UUID is a true no-op, retaining editor history, selections, masks and leases.
- No deletion/merge of profiles, reassignment of historical annotations, password recovery or identity-provider integration in this release. No fresh UUID is invented to work around a writer conflict.
- Rename preserves UUID and local profile creation time. A rename changes the local profile and the application's identity display. Project author display metadata is refreshed when that profile is used to open/join a writable project, and immediately on explicit rename of the active profile in a writable project. Never scan or rewrite other projects. If local rename succeeds but updating the current project's display metadata fails, report `昵称已保存在本机，项目显示名称未更新` with the error; keep the identity and all work intact. Reopening/reselecting after switching away retries the metadata refresh. Remote computers learn the project nickname via normal author polling; their locally stored nickname is not silently changed. View-only and ordinary projects do not receive author metadata writes.

## Profile persistence and transfer
- Introduce a focused Rust profile module under application-local data, independent of projects and usable before opening one. A versioned JSON store contains revision, last selected UUID and a bounded list of profiles `{authorId, displayName, createdAt}`. Profile UUID is the actual author ID in every project. New IDs use the existing UUID v4 generator.
- Store version 1, at most 128 profiles and 1 MiB serialized bytes; a portable single-profile JSON has a distinct kind/version and a 4 KiB limit. UUIDs are non-nil canonical strings; nickname trims surrounding whitespace, has 1–64 Unicode scalar values, at most 256 UTF-8 bytes, no control characters; timestamp is a valid UTC RFC3339 string. Reject unknown/duplicate fields, unsupported versions, duplicate UUIDs, oversized or malformed structures. Limits must be checked on both read and write.
- Profiles are plain identity metadata, not credentials. No DPAPI, Argon2, secret or private signing key. Export includes only the portable kind/version and one profile, never project paths, recordings, labels, workspace preferences, masks or pending edits. File pickers select import/export paths; cancellation has no effects. Export uses create-new/no-clobber semantics and reports an existing target rather than silently overwriting it. Retain existing safe-file/atomic-publication patterns and avoid executing any imported content.
- Import validates completely before mutation. The same UUID is idempotent: retain its existing local nickname/creation metadata and report that the identity already exists; do not duplicate, overwrite it or auto-select it. Same nickname with a different UUID is a separate identity. Import into an independent application-data directory keeps the exported UUID exactly.
- Use a short interprocess store lock, atomic replacement and revision checks to avoid lost concurrent additions/renames/selections. A corrupt existing store reports an error and is not silently reset or replaced with a fresh UUID. No migration from the old DPAPI file; leave it untouched.
- Each application process captures its current identity. Last-selected persistence supplies subsequent launches; another running instance changing that value never silently changes a live editor's identity. Refreshing the list can expose profiles and nickname edits without automatically rebinding the current author.

## Project representation and ownership
- New collaborative projects use manifest format 3 and credential-free public author records under `authors/<canonical UUID>.json`. Author record kind/version, project ID and `{authorId, displayName, createdAt}` are strictly validated; bounded enumeration retains the current 128-author limit. No account/login/passwordHash fields or accounts directory is created. Remove obsolete credential APIs and production dependencies once callers are switched.
- Preserve the media catalog version/append semantics, immutable audio copies, author layer payload/hash/revision semantics, local workspace layout and private editing behavior. Audit every literal `format_version == 2`/`!= 2` and corresponding frontend/native checks: the new current collaboration format must get catalog import, masks, volume, hidden-media, view-only, save/reopen and reconciliation behavior. Use a named current-format constant/capability at touched boundaries; do not reinterpret ProjectDocument, exchange or unrelated record version 2 as collaboration version 3.
- On writable open/create/copy/import, adopt the selected profile into the project, using its UUID directly, and acquire the existing per-project/per-author writer lease. Same identity can write different projects concurrently. A second writer for the same UUID/project fails clearly and retains explicit view-only opening; never steal a lease or create a substitute identity.
- Author-session validity uses stable project/root/UUID and lease facts, not equality of mutable nickname metadata. Other authors' layers remain read-only in ordinary UI/native editing. Overlapping annotations from different identities remain distinct. UUID is ownership routing, not a security credential; no anti-impersonation measures are required.
- Switching identities does not copy categories, notes, annotations, masks, hidden-file state, volume or history from the previous identity. Reopening that identity restores its own local workspace. Author identity files carry none of these private settings between computers. Shared project audio remains available under all identities.

## Native and frontend transitions
- Add typed profile list/create/rename/import/export/select operations usable with no project. Keep profile persistence logic outside React/localStorage. Native commands are authoritative; selection accepts an existing local UUID, not arbitrary caller-supplied author paths or payloads.
- Guards bind mutations to the observed profile-store revision and runtime expectation (nonce and optional project ID/revision). Stale requests, project replacement, closing and competing actions cannot bind the wrong editor. Use the existing operation admission/cancellation machinery; no NAS I/O on the UI thread or while holding the live project mutex.
- When a writable collaboration project is open, switching first drains current drafts, saves/publishes through the existing lifecycle and honors pending import/release/publication barriers. Failed saving, pending recovery, target writer contention, target workspace failure, cancellation or stale authority leave the old editor and selected identity active; never discard drafts silently.
- Prepare the target author/workspace while the old editor is retained, recheck authority/cancellation, then persist the selection and install prepared state as a guarded commit with no remaining fallible state-install step. An unused empty author registration after interrupted preparation is acceptable; copying or modifying any annotation payload is not. Cover failure at profile persistence and target preparation. Profile list mutations must not implicitly adopt a newly opened project.
- Profile management local writes are allowed with view-only/ordinary projects, but identity changes there do not promote view-only to writable or reinterpret the document as an author layer. Apply lifecycle admission as appropriate and keep document/actor state unchanged. The selected profile applies to future writable collaborative opens/copies.
- Active profile/global UI is distinct from nullable project actor/view-only state; avoid showing `访客` on the empty workspace. Disable conflicting actions while a transition is pending; keep errors actionable and cancel/retry semantics visible. Pure dialogs close on outside click/Escape; in-flight mutation uses explicit cancellation and ownership guards.

## Compatibility / Migration
- Backward compatibility: partial.
- Protected surfaces: ordinary ProjectDocument/exchange format 2, portable full-project/annotation exchange content, media bytes, annotation geometry/notes/categories, playback/spectrogram/selection behavior, private workspace separation, existing release artifacts.
- Allowed breakage: old collaboration manifest formats 1/2, project accounts, DPAPI auto-author identity and password IPC/UI. New collaboration format 3 is deliberately not opened by prior versions. Reject unsupported collaboration versions before any mutation, with a clear message to use the prior app or exchange/export workflow. Do not delete, migrate or rewrite old projects or identity files. Ordinary standalone project reading and conversion through existing copy/exchange functionality remain supported.
- Migration strategy: none. No compatibility account mode, hidden password path, format migration tool or background project conversion.
