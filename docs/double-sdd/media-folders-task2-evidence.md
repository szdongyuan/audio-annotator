## Native organization contract

`organization_get({binding:{runtimeNonce,projectId}})` returns `{runtimeNonce,projectId,organization}`. `organization_apply({binding:{runtimeNonce,projectId},expectedRevision,operation})` returns that same separate snapshot. `expectedRevision` is the organization revision, never the private document revision. The organization and operation DTOs are exactly the Task 1 types; nullable parentId/folderId fields are required. Operation discriminants are createFolder, renameFolder, moveFolder, removeFolder and moveMedia. Unknown request fields are rejected by the native serde DTOs.

The commands bind the current runtime, shared project/workspace and native repository. Reads work for view-only actors and while private recovery awaits a choice. Mutations require a held native author session, refuse recovery and use the existing Service job admission. Core CAS/lease/catalog/head validation remains authoritative. They never adopt a catalog, install an OpenProject, change ProjectDocument2, clear undo/redo, reset media generations or touch playback.

`CollaborationRepository::apply_organization_controlled<Guard>(session, expected_revision, operation, cancel, before_commit)` is a focused extension of the Task 1 method. It acquires the interprocess lock and completes catalog I/O before asking native code for a final guard. Native captures repository/Arc<AuthorSession> under state.0, releases it for lock wait/catalog I/O, and revalidates cancellation, owner/runtime, recovery and the same author session at precommit. The returned state.0 guard is retained only across the bounded atomic metadata write (at most 16 MiB, including sync/replacement). This final write uses the existing cancellation checks before write/sync/rename; cancellation after replacement cannot retract the committed result. The original core method remains a safe wrapper with a unit guard.

This bounded final-write mutex is an intentional authority tradeoff. Interprocess lock waits and potentially slow full catalog reads never hold the private editor mutex. Tests exercise actual lock contention and the real under-lock precommit gate, rather than only an after-I/O callback.

## Source config, candidates and full-result preview

Config now requires `organization:{targetFolderId:null|UUID,mode:'sourcePath'|'flat'|'template',wrapSource:boolean,stripComponents:string[],template:string}`. Discovery Rules and source token/event ownership remain unchanged. The minimal current controller/default fixture uses flat/root; the four meaningful complete presets and full configuration controls belong to Task 4.

- sourcePath retains native source-relative parent components, optionally prepending the selected folder basename or ZIP stem. stripComponents removes exact case-insensitive names from source-relative directories only. flat adds no relative folders. template expands exact whole-segment tokens; wrapSource applies to sourcePath because template explicitly controls source placement through {source}.
- Tokens: {source}, {relativeDir}, {record}, {date}, {result}, {faultType}, {model}, {route}. relativeDir may expand multiple components; other tokens expand one segment. Generic discovery rejects all manifest/route tokens during config validation, including dormant template values. No source I/O occurs for invalid config. Dot/empty/absolute Windows templates, embedded/unknown braces, invalid logical names and excessive depth are rejected.
- Metadata is read only from the already bounded valid jingcheng manifest. Before route retention, each optional metadata field is bounded to 128 scalars/512 bytes, with at most four invalid-field flags; dates parse only bounded RFC3339 input. An invalid field is reported/excludes a candidate only when its template token is used; unused invalid optional metadata keeps valid route audio. Values come from: containing manifest directory basename, RFC3339 run.accepted_at date, outcome.result, outcome.fault_type, run.model, and the manifest position mapping. Separators in metadata become underscores; strings are trimmed and generated names retain existing scalar/byte limits. No date/result/route inference uses archive names or CH filenames. Missing/non-string optional values and unparseable dates use 日期未知 / 未分类 / 型号未知 / 记录未知, emit bounded issues and retain otherwise valid audio. Invalid/overlong generated paths are excluded with issues, never truncated.
- Native candidate DTO adds `resultingFolderPath:string[]` and `originalFilename:string`. The path includes the captured existing target ancestry. originalFilename is the real source/ZIP entry basename captured before staging; displayName/source provenance remain independent.
- `import_source_page({token,offset,limit})` accepts 1–50 rows and returns `{candidates,issues,counts,folderSummary}`. Issues retain at most 256 messages; counts.issues reports the aggregate. folderSummary covers ALL accepted scan candidates, not the first page: at most 10000 indexed nodes `{index,parentIndex:null|number,name,mediaCount}`. Parents precede children; mediaCount includes descendants. Root is implicit and its total is counts.candidates. A 61-path regression proves folders after the first 50 media appear in the summary. Folder names, depth (16), candidate (10000), serialized head and existing source/manifest/audio budgets remain bounded.
- Native scan start captures layoutRevision, targetFolderId and target ancestry in the task registry. The project head is read in the blocking scan worker before source traversal; batch admission obtains one fresh immutable capture outside project/registry locks, validates the captured layout and seals all selected indices from that same capture before acquiring the existing preparation slot. Runtime, owner and source cancellation are checked again at that slot admission. All shared direct-file batches, including default root placement, use the same one-capture pattern; ordinary/relink paths retain the existing decoder path. The production import_source_page command is async/spawn_blocking because validating a page now reads the NAS organization head. Page requests and batch admission reject manual-layout changes. Batch admission resolves trusted task indices and creates non-serializable NativePlacementPlan capabilities before extraction/decoding. The new opaque NativePlacementCapture indexes existing siblings once; seal calls do no filesystem I/O or whole-head cloning per candidate. Scan preflight uses that capture to exclude paths that would exceed existing project folder capacity, retaining issues and coherent candidate indices. Ready media retain these plans through the native-only prepare_media_with_placement entry point, consuming the plan before staging and avoiding the root-placement fallback head read for every decoded item. PreparedCatalogMedia::with_placement remains available for existing native callers. The client receives only descriptors and cannot forge placement or original names. Publication rechecks the captured layout under the existing commit lock; concurrent additive imports reuse paths without advancing layoutRevision. Manual edits invalidate prepared publication. Committed retry acknowledges the current membership, preserving a subsequent move/rename.
- Preview release, cancellation, early events, media reservation, 256-item preparation batches, retained staged audio/PCM, acknowledgement retry and disposal-worker behavior are preserved. The controller gathers up to 256 candidates through bounded 50-row pages before starting the existing batch lifecycle; only 50 preview rows remain visible.

`CollaborationRepository::capture_media_placement(target_folder_id)` returns opaque `NativePlacementCapture` with `layout_revision()`, `target_path()` and `seal(relative_segments,original_filename)`. It has private fields, no serde and no Clone; plans remain non-serializable/non-Clone. The original single-plan sealer remains compatible and still performs its own fresh-head/layout validation. `prepare_media_with_placement(source,cache,cancel,plan,progress)` consumes a trusted sealed plan; all existing prepare/copy entry points remain compatible and still capture root placement before creating staging. A regression removes organization.json after capture and successfully seals multiple candidates and prepares decoded/copy media from the consumed sealed plan, proving neither stage reopens the head; publication still refuses an intervening manual layout change.
